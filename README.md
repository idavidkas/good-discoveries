# Хорошие открытия — GitLab Pages + PWA + Web Push

Русскоязычный научный сайт, в котором **одна свежая позитивная, прошедшая проверку новость занимает главное место**, а предыдущие статьи уходят в горизонтальную галерею миниатюр. Каждая миниатюра открывает подробный материал с DOI и ограничениями исследования. Работает на телефонах и компьютерах.

**Важно:** этот архив содержит **подготовленный к развёртыванию код**. Он ещё не опубликован в вашем GitLab или на хостинге. Чтобы получить живой сайт и настоящие уведомления, нужно запустить backend, подключить публичный HTTPS-адрес API и отправить файлы в ваш GitLab-репозиторий.

## Архитектура

```text
Crossref (научные журналы) -- каждые 15 минут --> FastAPI/SQLite --> утверждённые новости
                                                         |              |
                                                  /api/news     Push subscribers
                                                         |              |
                                                     HTTPS         каждые 72 часа
                                                         |              |
                             GitLab Pages (static HTML/CSS/JS/PWA) <-- Web Push
```

GitLab Pages **не поддерживает Python, SQLite и серверную отправку Push**. Поэтому статика развёртывается в GitLab Pages, а FastAPI с постоянной базой — на сервере с HTTPS (например, VPS). Backend необходим для живой ленты и уведомлений; без него Pages покажет явно помеченные демонстрационные материалы.

## Шаг 1. Запустить backend c HTTPS на VPS

Требуется сервер с Docker Compose и домен вида `api.example.org`. DNS A-запись домена должна указывать на VPS, порты 80/443 доступны извне.

```bash
cp .env.example .env
python -m pip install cryptography
python scripts/generate_vapid.py
```

Отредактировать `.env`:

```dotenv
API_HOST=api.example.org
FRONTEND_ORIGINS=https://YOURNAME.gitlab.io
VAPID_PRIVATE_KEY_FILE=/app/secrets/vapid_private.pem
VAPID_SUBJECT=mailto:actual-email@example.org
ADMIN_TOKEN=very-long-random-secret
CROSSREF_MAILTO=actual-email@example.org
OPENAI_API_KEY=
AUTO_PUBLISH=false
```

`FRONTEND_ORIGINS` содержит **origin** сайта GitLab Pages, без пути проекта, например `https://username.gitlab.io`; если GitLab выдаёт уникальный поддомен, использовать именно его. Для нескольких разрешённых адресов разделить запятой. `VAPID_SUBJECT` — действительный адрес отправителя. Не коммитить `.env` и `secrets/`.

```bash
docker compose -f compose.prod.yaml up -d --build
curl https://api.example.org/api/health
curl https://api.example.org/api/push/public-key
```

В `api/push/public-key` должно быть `"enabled":true` и непустой публичный ключ. Сохранять volume с БД и файл приватного VAPID-ключа: при их потере пропадут история/подписки, а смена ключа сделает старые подписки недействительными. Файл никогда не отдаётся браузеру.

Редакционная панель: `https://api.example.org/admin`. Доступ к действиям защищён `ADMIN_TOKEN`. Если `AUTO_PUBLISH=false`, найденные публикации попадают на ручную проверку и не публикуются без одобрения. Если AI-ключ пуст, автопубликация также отключена. **Аннотация статьи не равна независимой репликации.**

## Шаг 2. Создать проект GitLab Pages

1. Создать пустой репозиторий в GitLab (например, `good-discoveries`).
2. В `Settings → CI/CD → Variables` указать `API_BASE_URL=https://api.example.org`. Это публичный адрес, **не секрет**. В `Settings → General` убедиться, что Pages разрешён.
3. Запушить содержимое этого проекта в GitLab (все файлы, кроме `.env`, `secrets/`, `data/`, `public/`):

```bash
git init
git branch -M main
git add .
git commit -m "GitLab Pages PWA with 72h scientific push digests"
git remote add origin git@gitlab.com:YOURNAME/good-discoveries.git
git push -u origin main
```

4. В `Build → Pipelines` проверить выполнение jobs `backend-tests` и `pages`. Затем в `Deploy → Pages` взять **реальный URL** сайта: это может быть `https://YOURNAME.gitlab.io/good-discoveries/` или выделенный Pages-домен. Обязательно сверить origin и `FRONTEND_ORIGINS` на API. GitLab Pages сам публикует только содержимое `public/`, которое формирует `scripts/build_pages.py`; редакторские скрипты и секреты в сборку не попадают.

Поддомен проекта/домен GitLab Pages и `api.example.org` оба должны работать по HTTPS, иначе Web Push не заработает.

## Шаг 3. Установить PWA и включить уведомления

**iPhone (iOS 16.4+):** открыть публичный Pages-сайт в Safari → `Поделиться` → `На экран «Домой»` → открыть **установленную иконку** → нажать `Дайджест каждые 3 дня` → разрешить уведомления. С обычной открытой вкладки Safari на iPhone push не работает — приложение должно быть установлено на домашний экран.

**Android / Desktop:** открыть сайт по HTTPS → `Установить приложение` (или пункт установки в меню браузера) → открыть приложение → нажать `Дайджест каждые 3 дня` → разрешить уведомления.

На странице есть кнопка отключения уведомлений. Backend хранит подписки в SQLite, секретные ключи подписки никогда не выкладываются в GitLab Pages и не включаются в публичную ленту.

### Периодичность

- Проверка новых исследований: раз в **15 минут** независимо от открытой вкладки, пока backend работает.
- Первая отправка дайджеста: спустя **72 часа после подписки**, затем каждые 72 часа после успешной отправки. Планировщик проверяет просроченные доставки каждые 15 минут, то есть возможен небольшой сдвиг времени, а при недоступности сервера и дольше.
- Сводка: количество утверждённых статей, опубликованных **на сайте** с предыдущего дайджеста, и до трёх коротких заголовков. Нажатие открывает PWA.
- Если новостей за период нет, приходит одно уведомление об отсутствии проверенных новых публикаций. Старую новость не выдаём за новую.
- Ошибки доставки повторяются, мёртвые подписки (404/410) удаляются. Период рассчитывается **для каждого устройства отдельно**; пуши не приходят сразу после каждой новой новости.

Для промышленных нагрузок и больших аудиторий лучше PostgreSQL и отдельная очередь заданий: в MVP рассчитано на **один backend-процесс** и SQLite, без независимого сервиса диспетчеризации.

## Локальный запуск

```bash
cp .env.example .env
# Только локальный просмотр API без push:
docker compose up -d --build
# http://localhost:8000/
```

Для разработки отдельной статики:

```bash
python scripts/build_pages.py            # без API_BASE_URL собирает demo-режим
cd public && python -m http.server 8080  # http://localhost:8080/
```

Для проверки настоящей сборки Pages:

```bash
API_BASE_URL=https://api.example.org python scripts/build_pages.py
```

**Без работающего API** новости в Pages будут демонстрационными, а реальная доставка уведомлений недоступна — это явно указано в интерфейсе.

## Тесты

```bash
pip install -r requirements.txt pytest
pytest -q
node --check static/assets/app.js
node --check static/assets/pwa.js
node --check static/sw.js
```

11 тестов покрывают загрузку ленты, API-администрирование, подписку, SSRF-проверку endpoint, расписание на 72 часа, отсутствие дублирования уведомлений, формирование сводки и сборку Pages. Настоящая доставка на iPhone/Android требует E2E-проверки на устройстве с работающим публичным HTTPS API и валидной подпиской.

## Безопасность и ограничения

- В GitLab не загружать `.env`, файл ключа `secrets/vapid_private.pem`, БД или API-токены.
- Для публичного запуска настроить rate limiting входящих запросов к подпискам на reverse proxy или через WAF; у приложения пока только базовая серверная валидация endpoint.
- База SQLite и планировщик не рассчитаны на горизонтальное масштабирование без отдельного диспетчера.
- В демонстрационном наборе иллюстрации **оригинальные тематические SVG**, а не изображения самих научных опытов.
- Проверка из Crossref и AI-фильтр по аннотации не заменяют редакционную проверку полного текста и достоверности открытия. Значение `AUTO_PUBLISH=false` оставлено по умолчанию.
